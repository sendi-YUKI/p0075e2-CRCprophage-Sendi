# Sendi如何查看分析步骤、找到参数并重画结果

Jinlong负责正式研究的计算分析，并把实际使用的数据、代码、参数和结果交接给Sendi。Sendi应当能随时看懂每一步在做什么，从一张图找到它的数据和生成命令，并判断修改某个参数后需要重算哪些结果。后续实验由Sendi和实验团队围绕选定对象开展。

Jinlong可以使用自己的成熟pipeline。这里说明需要留下哪些记录，不要求另建一套审批或手工填表系统，也不增加新的pilot。现有workflow能导出的命令、配置、日志和文件清单，可以直接作为记录；模板用于补齐缺少的对应关系。

## 1. Jinlong每完成一部分分析，需要交给Sendi什么

Jinlong应随完成的分析更新小文件，避免只在最后交付几张图。Sendi收到这些文件后，应能区分哪些步骤已完成、哪些正在处理、哪些因输入或信息不足没有结果。

| 交给Sendi的小文件 | 具体内容 | Sendi可以据此做什么 |
|---|---|---|
| 实际流程说明和当前状态 | 每步的目的、输入、工具、输出、依赖步骤；已完成、失败及待处理内容 | 看懂分析进展，知道某张表从哪一步产生 |
| 自写或修改的代码 | 工作流入口、分析及绘图脚本、必要模块、代码commit；未提交的实际修改也保存为代码快照或差异文件 | 阅读实际实现，找到修改位置 |
| 实际生效配置和环境记录 | 工具版本、完整生效参数、默认值、命令行覆盖、依赖或容器；数据库版本、来源和校验单独记录 | 确认该次真正使用了什么，而不是只看到建议参数 |
| 输入清单和运行记录 | 供者／参考／目录身份、文件校验、完整命令、工作目录、运行时间、状态、失败原因及重试对应 | 找到原命令，判断某批结果能否复用 |
| 关键结果表及字段说明 | 原始ID、序列／位点／基因关系、过滤前后结果、有效分母、效应及全部P／Q；零、NA和失败原因分别保留 | 查看图中对象的完整数据，理解没有显示的结果 |
| 图、图源数据和生成记录 | PNG及适合编辑或排版的SVG／PDF，实际绘图输入表、显示筛选规则、脚本、配置和完整命令 | 改图样式、核对选图规则或重新生成图 |
| 大文件索引 | 服务器上序列、比对、数据库等文件的逻辑位置、校验和保存状态 | 需要时找到文件，不必把大文件全部下载到本地 |

代码、配置、表图和这些记录可以放入交付目录及版本库。Jinlong应保留每次实际运行的配置快照，让旧结果始终对应旧配置；修改当前配置时，不能同时把旧运行的配置改掉。方法说明可以随结果更新，不能把未运行的模板或拟采用的方案写成已经完成。

如果Jinlong已有清楚的目录，可以直接沿用。没有既定结构时，可以按用途安排：

```text
workflow/       工作流入口、自写或修改的代码、环境说明
config/         本次生效配置，以及各次运行的配置快照
manifests/      输入身份、纳排、文件校验、参考和目录版本
run_records/    完整命令、日志、状态和失败重试记录
results/        关键结果表、字段说明和结果之间的对应关系
figures/        图、实际绘图源表、显示设置和图的生成记录
reports/        实际流程、Methods、当前结果与待完成内容
data_index/     服务器大文件的位置、校验和保存记录
```

## 2. 现有模板分别记录什么

以下链接指向可直接使用的模板。Jinlong可以自动生成同样的信息，也可以将现有workflow导出文件的位置写进索引；不必把同一条命令、参数或文件路径人工抄进多张表。

| Sendi想知道的事情 | 对应模板 | 主要字段或内容 |
|---|---|---|
| 每一步为什么做，先做什么、后做什么 | [实际流程说明](templates/ACTUAL_WORKFLOW.template.md)、[步骤索引](templates/workflow_steps.template.tsv) | `stage`、`purpose`、`depends_on_stages`、`input_refs`、`entrypoint`、`config_refs`、`actual_status`、`run_record_refs`、`modification_entry` |
| Jinlong为什么选这个方法或阈值 | [方法与参数决策表](Jinlong_方法与参数决策表.tsv) | `decision_id`、`Jinlong_choice`、`rationale`、`config_path_and_key`、`actual_run_evidence`；建议、决定与实际运行值分开 |
| 这次究竟用了什么参数，在哪里改 | [实际参数记录](templates/actual_parameters.template.tsv) | `run_id`、`parameter_key`、`effective_value`、`origin_default_or_override`、`config_file`、`edit_file`、`config_key`、`plain_language_meaning`、`change_effect`、`rerun_from_stage` |
| 原命令是什么，运行成功了吗 | [运行记录](templates/run_records.template.tsv) | `run_id`、`stage`、`code_commit`、`input_manifest`、`command_file`、`effective_config`、`workdir`、`status`、`exit_code`、`log_path`、`failure_reason`、`retry_of`、`resume_command_file` |
| 工具和数据库分别是哪一版 | [软件与数据库记录](templates/software_database.template.tsv) | `resource_id`、`kind_tool_or_database`、`name`、`version`、`source_url`、`sha256_or_container_digest`、`version_command_output`、`lock_or_manifest` |
| 一张图用了哪张表、哪个脚本 | [图的生成记录](templates/figure_provenance.template.tsv) | `figure_id`、`figure_file`、`source_data`、`source_data_sha256`、`script`、`script_sha256`、`command`、`config`、`input_run_ids`、`statistical_family` |
| 一张结果表来自哪次分析，使用哪个目录版本 | [结果索引](templates/result_provenance.template.tsv) | `result_id`、`relative_path`、`upstream_result_ids`、`producer_run_ids`、`catalog_version`、`description_or_dictionary`、`regeneration_entry` |
| 大文件在哪里，是否还保留，怎样重建 | [大文件索引](templates/large_file_index.template.tsv) | `logical_id`、`path_alias`、`bytes`、`sha256`、`retained`、`producer_run_id`、`retention_policy`、`rebuild_command`、`checksum_status`、`local_sync_status` |
| 一次修改改变了什么，已经重算哪些结果 | [变更记录](templates/change_log.template.tsv) | `old_value`、`new_value`、`reason`、`config_or_code_diff`、`affected_stages`、`affected_results`、`rerun_from_stage`、`rerun_run_ids` |

供者、正式参考、prophage实例及联合目录的字段和冻结记录，使用[正式研究交付清单](../04_deliverables/交付清单与表字段.md)。正式参考与联合目录各自使用自己的`freeze_id`，结果还应能对应到实际使用的目录版本。

## 3. Sendi如何从一张结果图找到数据、代码和参数

Sendi可以按下面的顺序查找。Jinlong在交付图文件时保留`figure_id`，并在图的生成记录中写清相应文件名。

1. **Sendi先查这张图的记录。** 用`figure_id`在`figure_provenance`中找到`figure_file`，再打开`source_data`对应的绘图输入表。表中的样本或对象ID应能连接到完整结果表；如果图只显示一部分对象，生成记录或图注应说明选择顺序和规则。
2. **Sendi找到绘图脚本和命令。** `script`指出脚本位置，`command`保存生成该图的完整命令，`config`指出颜色、字体、面板和其他绘图设置。`script_sha256`和`source_data_sha256`用于确认文件是否仍与这张图一致。
3. **Sendi找到产生图中数据的运行。** 按`input_run_ids`到`run_records`查对应的`run_id`，查看`stage`、`command_file`、`workdir`、`code_commit`及`effective_config`。这一步区分“生成图的命令”和“产生统计结果的命令”。
4. **Sendi查看某个参数的实际值和修改位置。** 在该运行的`actual_parameters`中查`effective_value`及其含义，再用`edit_file`和`config_key`找到修改入口。默认值或命令行覆盖由`origin_default_or_override`说明。方法选择的理由见对应`decision_id`。
5. **Sendi需要继续向上游追溯时，打开输入清单。** `input_manifest`和结果索引连接上游输入及`producer_run_ids`；工具和数据库由运行记录中的`software_database_resource_ids`对应到版本记录；大型输入由`large_file_index`定位。

例如，下面展示一组**假设的对应关系，仅用于说明查找方法，不是已经运行的分析，也不是项目中现有文件**：

| Sendi正在查看的记录 | 示例内容 | 下一步 |
|---|---|---|
| 图的`figure_id` | `FIG_EXAMPLE_01` | 在图的生成记录中找到这一行 |
| 该图的`source_data` | `results/example_effects.tsv` | 查看图中效应值和对象ID |
| 该图的`script`和`config` | `workflow/plot_example.py`、`config/example_plot.yaml` | 修改外观时查看这两个文件，并使用该行的绘图`command` |
| 该图的`input_run_ids` | `RUN_EXAMPLE_STATS_01` | 在运行记录中找到生成效应表的分析 |
| 该运行的`command_file`和`effective_config` | `run_records/RUN_EXAMPLE_STATS_01/command.txt`、`run_records/RUN_EXAMPLE_STATS_01/effective_config.yaml` | 查看实际统计命令和当次生效参数 |
| 该运行的参数修改入口 | `actual_parameters`中的`edit_file`、`config_key` | 找到当前可编辑配置，并先判断修改影响范围 |

在这个例子中，Sendi只想调整图中文字大小，就查看绘图配置；Sendi想改变统计模型，就查看产生效应表的分析配置。Jinlong不能把两个入口混写成一个含糊的“参数文件”。

## 4. 实际配置要保存到什么程度

完整命令很重要，但命令中没有显式写出的选项仍可能采用工具默认值。因此，Jinlong应优先保存工具或workflow导出的完整生效配置，包含默认值、配置文件值和命令行覆盖后的最终结果，并记录工具版本。工具不能自动导出全部生效值时，Jinlong应结合该固定版本的默认配置或帮助输出，补足影响结果的默认参数，并注明来源。

对每个影响结果的主要参数，Sendi至少应能读懂：它控制什么、实际值是多少、单位及比较方向是什么、分母或适用对象是什么、在哪里修改、修改后从哪一步重算。例如“覆盖≥75%”还需要说明分母是整条病毒参考还是特异区段，以及达到覆盖的位点深度要求；单独记录`0.75`不足以解释测量。

`actual_parameters`可以由上述配置自动导出，作为便于查询的索引。Jinlong不需要手工重复录入所有CLI选项，但导出的表与实际配置应保持一致。工具版本和数据库版本必须分开记录，同一工具更新数据库也可能改变结果。随机种子、环境锁定或容器摘要也应随实际运行保存。

资源记录区分“申请”和“实测”：`threads_requested`、`memory_requested_gib`记录申请值，`elapsed_seconds`、`peak_memory_gib`记录实际观测值。没有采集实际峰值时应如实注明未记录，不能把申请内存当作实际消耗。失败与重试保留原`run_id`及`retry_of`关系，恢复命令放在`resume_command_file`，便于Sendi理解结果来自哪次成功运行。

## 5. Sendi想修改一项内容时，哪些步骤需要重跑

Jinlong先查看修改涉及的输入、配置和步骤依赖，再从受影响的最早一步开始重算。下面的表用于判断范围；具体起点仍以实际pipeline保存了哪些中间结果为准。

| 想修改什么 | 通常从哪里重新计算 | 可以继续使用什么 | 需要特别看清的地方 |
|---|---|---|---|
| 图的字体、颜色、尺寸、图例或面板排列 | 只运行绘图脚本 | 原测量表和统计结果 | 如果改了展示对象或筛选顺序，也要更新图注和显示规则；不能把这种筛选当成新的统计检验 |
| 统计模型、协变量、信息过滤或多重校正范围 | 从固定的供者测量矩阵和临床表重跑相应统计，再重画图 | 未受影响的组装、比对和测量 | 保留新的模型、分母、完整检验集合和P／Q，不能只重算有利的几个对象 |
| 将Sendi试跑曾用的75%检出广度改为另一个值 | 若已保存实际广度、归属片段和歧义等充分信息，可直接重新判定全部状态，再重跑依赖这些状态的统计和图 | 相同参考、相同比对和相同归属规则下的测量信息 | 同时重新判断检出、未达规则和NA；只有旧的0／1结果时不够，需要恢复更早的测量信息。75%是旧试跑值，不是本文件要求正式研究采用的数值 |
| MAPQ、identity、baseQ过滤或多重比对的reads归属规则 | 从保存了所需候选比对的文件重新做过滤、归属和覆盖计算，再更新状态、统计与图 | 与新规则兼容且信息完整的原比对 | 如果原文件已丢弃新规则需要的比对，或改变了比对搜索、参考索引等设置，就需要重新比对；不能仅修改结果表中的参数标签 |
| 参考序列、prophage边界、目录成员、代表序列或竞争背景 | 从改变的参考／预测／目录步骤产生新版本，再统一更新依赖它的测量、统计和图 | 输入及规则均未改变、且经记录确认可复用的上游结果 | 新竞争序列也可能改变旧目标的reads归属；不能把新对象的几列直接拼入旧矩阵。仅补文字注释而未改测量序列或规则时，不必因此重新比对 |
| 供者输入合并、reads质控、去人源或组装方法 | 从被修改的步骤重跑受影响供者，再更新相关下游 | 未受影响供者或步骤的兼容结果 | 若新的发现结果进一步改变联合目录，还需按上一行更新所有依赖新目录的测量，不能只更新新供者 |

Jinlong应保存修改前后的配置或代码差异、理由、受影响结果和新运行ID；现有[变更记录模板](templates/change_log.template.tsv)可以承接这些信息。旧结果仍指向旧运行，新结果使用新版本，Sendi才能比较两次结果而不混淆。

常规工具和参数由Jinlong决定。若修改涉及临床分组、开发／保留队列角色或研究问题，Jinlong应与Sendi讨论科学含义；这种讨论不需要延伸成每次改图或调整资源都要审批的流程。

## 6. Sendi可以怎样尝试重画一张已有结果图

现有[复制候选重画脚本](tools/redraw_replication.py)读取交付包中的[两条复制候选底表](../05_existing_results/postpilot_diagnostics/05_replication_activity/replication_candidates.tsv)，不需要连接原服务器。从交接包根目录（本地`analysis2/`，或下载后的GitHub仓库根目录），在已安装matplotlib的Python环境中，可以运行：

```bash
python 03_execution/tools/redraw_replication.py --out-dir redraw_output
```

命令会生成PNG和SVG。该脚本是用真实底表生成候选概览的简单例子，不是原11张图的完整复刻。Sendi可以查看脚本中的字体、颜色、尺寸设置，并把新图写入自己的输出目录；这类修改不需要重组装、重新比对或重新估计覆盖。

Sendi试跑的11张原图、图注和对应方法见[Sendi试跑报告](../05_existing_results/CRC-PHIRE_Sendi试跑方法结果与正式研究参考.md)及[图注与测量统计方法](../05_existing_results/图注与测量统计方法.md)。原绘图代码保留实际选择和计算逻辑；完整重画还需要按说明配置其数据根和所需输入。Jinlong的新结果也应提供同样明确的数据入口和重画命令。

## 7. 哪些大文件留服务器，清理时怎样保留可追溯性

原始及clean FASTQ、参考与患者组装FASTA、大型病毒／侧翼序列、关键BAM及索引、marker mapout、数据库和大型工具中间输出，可以保留在服务器。Sendi本地需要能读懂的小表、代码、配置和图，以及定位这些大文件的索引；不要求把每份大文件复制进Git或反复复制到多个结果目录。

Jinlong在[大文件索引](templates/large_file_index.template.tsv)中为文件记录稳定的`logical_id`、逻辑路径`path_alias`、大小`bytes`、校验`sha256`、生成它的`producer_run_id`及保存状态`retained`。索引还应说明保存安排`retention_policy`、可用的重建命令`rebuild_command`，以及校验和本地同步是否完成。服务器连接方式、账号或内部地址通过双方约定的私下渠道交接，公开记录使用可解释的路径别名。

最终参考序列、患者组装、prophage区段／侧翼／坐标、关键BAM及索引、目录成员、基因和系统结果、图源表及代码配置，应按既定保存安排保留。它们分别支持后续确认序列身份、检查边界、补充注释、比较覆盖或重画，不能因为图已画完就一起清除。

Jinlong清理重要大文件或工具临时目录前，应先沿步骤依赖确认后续分析是否还会使用它，再确认保留的输入、代码、数据库版本和命令足以重建所需结果。清理后更新索引，写清实际删除了什么、是否有其他保留副本、重建从哪一步开始。保留最终汇总表不等于保存了全部原始明细；没有备份或无法直接恢复时，应如实记录，方便Sendi判断日后补查的工作量。
