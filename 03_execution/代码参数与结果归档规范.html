Jinlong负责正式研究的计算分析，并把实际使用的数据、代码、参数和结果交接给Sendi。Sendi应当能随时看懂每一步在做什么，从一张图找到它的数据和生成命令，并判断修改某个参数后需要重算哪些结果。后续实验由Sendi和实验团队围绕选定对象开展。

Jinlong可以使用自己的成熟pipeline。这里说明需要留下哪些记录，不要求另建一套审批或手工填表系统，也不增加新的pilot。现有workflow能导出的命令、配置、日志和文件清单，可以直接作为记录；模板用于补齐缺少的对应关系。

1. Jinlong每完成一部分分析，需要交给Sendi什么

Jinlong应随完成的分析更新小文件，避免只在最后交付几张图。Sendi收到这些文件后，应能区分哪些步骤已完成、哪些正在处理、哪些因输入或信息不足没有结果。

交给Sendi的小文件具体内容Sendi可以据此做什么
实际流程说明和当前状态每步的目的、输入、工具、输出、依赖步骤；已完成、失败及待处理内容看懂分析进展，知道某张表从哪一步产生
自写或修改的代码工作流入口、分析及绘图脚本、必要模块、代码commit；未提交的实际修改也保存为代码快照或差异文件阅读实际实现，找到修改位置
实际生效配置和环境记录工具版本、完整生效参数、默认值、命令行覆盖、依赖或容器；数据库版本、来源和校验单独记录确认该次真正使用了什么，而不是只看到建议参数
输入清单和运行记录供者／参考／目录身份、文件校验、完整命令、工作目录、运行时间、状态、失败原因及重试对应找到原命令，判断某批结果能否复用
关键结果表及字段说明原始ID、序列／位点／基因关系、过滤前后结果、有效分母、效应及全部P／Q；零、NA和失败原因分别保留查看图中对象的完整数据，理解没有显示的结果
图、图源数据和生成记录PNG及适合编辑或排版的SVG／PDF，实际绘图输入表、显示筛选规则、脚本、配置和完整命令改图样式、核对选图规则或重新生成图
大文件索引服务器上序列、比对、数据库等文件的逻辑位置、校验和保存状态需要时找到文件，不必把大文件全部下载到本地

代码、配置、表图和这些记录可以放入交付目录及版本库。Jinlong应保留每次实际运行的配置快照，让旧结果始终对应旧配置；修改当前配置时，不能同时把旧运行的配置改掉。方法说明可以随结果更新，不能把未运行的模板或拟采用的方案写成已经完成。

如果Jinlong已有清楚的目录，可以直接沿用。没有既定结构时，可以按用途安排：

workflow/       工作流入口、自写或修改的代码、环境说明
config/         本次生效配置，以及各次运行的配置快照
manifests/      输入身份、纳排、文件校验、参考和目录版本
run_records/    完整命令、日志、状态和失败重试记录
results/        关键结果表、字段说明和结果之间的对应关系
figures/        图、实际绘图源表、显示设置和图的生成记录
reports/        实际流程、Methods、当前结果与待完成内容
data_index/     服务器大文件的位置、校验和保存记录

3. Sendi如何从一张结果图找到数据、代码和参数

Sendi可以按下面的顺序查找。Jinlong在交付图文件时保留figure_id，并在图的生成记录中写清相应文件名。

  1. Sendi先查这张图的记录。 用figure_id在figure_provenance中找到figure_file，再打开source_data对应的绘图输入表。表中的样本或对象ID应能连接到完整结果表；如果图只显示一部分对象，生成记录或图注应说明选择顺序和规则。
  2. Sendi找到绘图脚本和命令。 script指出脚本位置，command保存生成该图的完整命令，config指出颜色、字体、面板和其他绘图设置。script_sha256和source_data_sha256用于确认文件是否仍与这张图一致。
  3. Sendi找到产生图中数据的运行。 按input_run_ids到run_records查对应的run_id，查看stage、command_file、workdir、code_commit及effective_config。这一步区分“生成图的命令”和“产生统计结果的命令”。
  4. Sendi查看某个参数的实际值和修改位置。 在该运行的actual_parameters中查effective_value及其含义，再用edit_file和config_key找到修改入口。默认值或命令行覆盖由origin_default_or_override说明。方法选择的理由见对应decision_id。
  5. Sendi需要继续向上游追溯时，打开输入清单。 input_manifest和结果索引连接上游输入及producer_run_ids；工具和数据库由运行记录中的software_database_resource_ids对应到版本记录；大型输入由large_file_index定位。

图的figure_idFIG_EXAMPLE_01在图的生成记录中找到这一行
该图的source_dataresults/example_effects.tsv查看图中效应值和对象ID

在这个例子中，Sendi只想调整图中文字大小，就查看绘图配置；Sendi想改变统计模型，就查看产生效应表的分析配置。Jinlong不能把两个入口混写成一个含糊的“参数文件”。

4. 实际配置要保存到什么程度

完整命令很重要，但命令中没有显式写出的选项仍可能采用工具默认值。因此，Jinlong应优先保存工具或workflow导出的完整生效配置，包含默认值、配置文件值和命令行覆盖后的最终结果，并记录工具版本。工具不能自动导出全部生效值时，Jinlong应结合该固定版本的默认配置或帮助输出，补足影响结果的默认参数，并注明来源。

对每个影响结果的主要参数，Sendi至少应能读懂：它控制什么、实际值是多少、单位及比较方向是什么、分母或适用对象是什么、在哪里修改、修改后从哪一步重算。例如“覆盖≥75%”还需要说明分母是整条病毒参考还是特异区段，以及达到覆盖的位点深度要求；单独记录0.75不足以解释测量。

actual_parameters可以由上述配置自动导出，作为便于查询的索引。Jinlong不需要手工重复录入所有CLI选项，但导出的表与实际配置应保持一致。工具版本和数据库版本必须分开记录，同一工具更新数据库也可能改变结果。随机种子、环境锁定或容器摘要也应随实际运行保存。

资源记录区分“申请”和“实测”：threads_requested、memory_requested_gib记录申请值，elapsed_seconds、peak_memory_gib记录实际观测值。没有采集实际峰值时应如实注明未记录，不能把申请内存当作实际消耗。失败与重试保留原run_id及retry_of关系，恢复命令放在resume_command_file，便于Sendi理解结果来自哪次成功运行。

5. Sendi想修改一项内容时，哪些步骤需要重跑

Jinlong先查看修改涉及的输入、配置和步骤依赖，再从受影响的最早一步开始重算。下面的表用于判断范围；具体起点仍以实际pipeline保存了哪些中间结果为准。

想修改什么通常从哪里重新计算可以继续使用什么需要特别看清的地方
图的字体、颜色、尺寸、图例或面板排列只运行绘图脚本原测量表和统计结果如果改了展示对象或筛选顺序，也要更新图注和显示规则；不能把这种筛选当成新的统计检验
统计模型、协变量、信息过滤或多重校正范围从固定的供者测量矩阵和临床表重跑相应统计，再重画图未受影响的组装、比对和测量保留新的模型、分母、完整检验集合和P／Q，不能只重算有利的几个对象
将Sendi试跑曾用的75%检出广度改为另一个值若已保存实际广度、归属片段和歧义等充分信息，可直接重新判定全部状态，再重跑依赖这些状态的统计和图相同参考、相同比对和相同归属规则下的测量信息同时重新判断检出、未达规则和NA；只有旧的0／1结果时不够，需要恢复更早的测量信息。75%是旧试跑值，不是本文件要求正式研究采用的数值
MAPQ、identity、baseQ过滤或多重比对的reads归属规则从保存了所需候选比对的文件重新做过滤、归属和覆盖计算，再更新状态、统计与图与新规则兼容且信息完整的原比对如果原文件已丢弃新规则需要的比对，或改变了比对搜索、参考索引等设置，就需要重新比对；不能仅修改结果表中的参数标签
参考序列、prophage边界、目录成员、代表序列或竞争背景从改变的参考／预测／目录步骤产生新版本，再统一更新依赖它的测量、统计和图输入及规则均未改变、且经记录确认可复用的上游结果新竞争序列也可能改变旧目标的reads归属；不能把新对象的几列直接拼入旧矩阵。仅补文字注释而未改测量序列或规则时，不必因此重新比对
供者输入合并、reads质控、去人源或组装方法从被修改的步骤重跑受影响供者，再更新相关下游未受影响供者或步骤的兼容结果若新的发现结果进一步改变联合目录，还需按上一行更新所有依赖新目录的测量，不能只更新新供者

Jinlong应保存修改前后的配置或代码差异、理由、受影响结果和新运行ID；现有变更记录模板可以承接这些信息。旧结果仍指向旧运行，新结果使用新版本，Sendi才能比较两次结果而不混淆。

常规工具和参数由Jinlong决定。若修改涉及临床分组、开发／保留队列角色或研究问题，Jinlong应与Sendi讨论科学含义；这种讨论不需要延伸成每次改图或调整资源都要审批的流程。

6. Sendi可以怎样尝试重画一张已有结果图

现有复制候选重画脚本读取交付包中的两条复制候选底表，不需要连接原服务器。从交接包根目录（本地analysis2/，或下载后的GitHub仓库根目录），在已安装matplotlib的Python环境中，可以运行：

python 03_execution/tools/redraw_replication.py --out-dir redraw_output

命令会生成PNG和SVG。该脚本是用真实底表生成候选概览的简单例子，不是原11张图的完整复刻。Sendi可以查看脚本中的字体、颜色、尺寸设置，并把新图写入自己的输出目录；这类修改不需要重组装、重新比对或重新估计覆盖。

Sendi试跑的11张原图、图注和对应方法见Sendi试跑报告及图注与测量统计方法。原绘图代码保留实际选择和计算逻辑；完整重画还需要按说明配置其数据根和所需输入。Jinlong的新结果也应提供同样明确的数据入口和重画命令。

7. 哪些大文件留服务器，清理时怎样保留可追溯性

原始及clean FASTQ、参考与患者组装FASTA、大型病毒／侧翼序列、关键BAM及索引、marker mapout、数据库和大型工具中间输出，可以保留在服务器。Sendi本地需要能读懂的小表、代码、配置和图，以及定位这些大文件的索引；不要求把每份大文件复制进Git或反复复制到多个结果目录。

Jinlong在大文件索引中为文件记录稳定的logical_id、逻辑路径path_alias、大小bytes、校验sha256、生成它的producer_run_id及保存状态retained。索引还应说明保存安排retention_policy、可用的重建命令rebuild_command，以及校验和本地同步是否完成。服务器连接方式、账号或内部地址通过双方约定的私下渠道交接，公开记录使用可解释的路径别名。

最终参考序列、患者组装、prophage区段／侧翼／坐标、关键BAM及索引、目录成员、基因和系统结果、图源表及代码配置，应按既定保存安排保留。它们分别支持后续确认序列身份、检查边界、补充注释、比较覆盖或重画，不能因为图已画完就一起清除。

Jinlong清理重要大文件或工具临时目录前，应先沿步骤依赖确认后续分析是否还会使用它，再确认保留的输入、代码、数据库版本和命令足以重建所需结果。清理后更新索引，写清实际删除了什么、是否有其他保留副本、重建从哪一步开始。保留最终汇总表不等于保存了全部原始明细；没有备份或无法直接恢复时，应如实记录，方便Sendi判断日后补查的工作量。
